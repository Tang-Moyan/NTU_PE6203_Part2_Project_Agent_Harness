## 3. 重要边界：不要自建 Tools / Sandbox

课题要求把审批网关接入 **AgentDojo** 评测流水线。因此：

### 3.1 正式评测：复用 AgentDojo，不要自己造环境

| 你们需要的东西 | 从哪里来 | 要不要自己写 |
| :--- | :--- | :--- |
| 工具（读邮件、转账、改文件等） | AgentDojo 各 suite 自带 | **不需要**自研一套 tools |
| Sandbox / 模拟环境状态 | AgentDojo 环境（邮箱、银行、工作区等） | **不需要**自建 sandbox |
| 任务说明、攻击场景、成功判定 | AgentDojo benchmark | **不需要**自编主评测集 |
| 环境内的文件 / 账户等内容 | AgentDojo 任务初始化提供 | **不需要**在本仓库维护业务文件树 |
| Approval Gate 拦截接入 | `agentdojo_integration/`（汤墨言主责） | 你们调用，一般不重写底层 |
| TCR / HITL / Token / 归因 / 报告 | `evaluation/` + `results/` | **这才是你们的主交付** |

**不要做的事：**

- 为了“方便测试”另起一套自研文件系统 sandbox、假邮件服务器、假数据库，并把它当成正式基准
- 用自制任务集替代 AgentDojo 报告 TCR@k（结果不可比，也不符合课题表述）

**原因：** 正式数字必须来自同一 benchmark，才能和 Full-approve / Full-escalate / Smart Policy 公平对比。

### 3.2 开发早期：只允许轻量合成替身（可选）

在汤墨言尚未完成 AgentDojo 接入前，可以用合成数据把**指标与归因代码**先跑通，例如：

- 已有：`scripts/smoke_evaluation.py`（合成 `ToolCall` + 假任务结果 → 验证 TCR/HITL/归因汇总）
- 可选：少量假轨迹 JSON，用于练手 Failure Case 分类

这些**只用于联调 / 单测**，不能当作最终实验结论。AgentDojo 接通后，主实验必须切到真实 suite。

### 3.3 和“文件内容”相关的边界

- **算分时**：评测脚本可以读取 AgentDojo 的 ground-truth / 攻击标签（评估者权限）
- **给 Policy / Reviewer 时**：`TaskContext` 仍须脱敏，禁止泄漏 Oracle
- **本仓库产出**：主要是 `results/`、`case_studies/`、图表、README/Report，而不是再造业务数据目录

### 3.4 和汤墨言的分工接口

1. 汤墨言提供：AgentDojo 工具拦截、`TaskContext` 构造方式、如何从一次 run 取出“任务是否成功 / 是否执行未授权操作”

## 4. 主指标说明

### 4.1 TCR@k（Safe Task Completion Rate）

在预算上限为 `k` 时：安全完成任务数 / 总任务数。

代码对应字段（已在 `metrics.py`）：

- `task_completed`
- `unauthorized_executed`
- `safe_completed = task_completed and not unauthorized_executed`
- `BenchmarkSummary.tcr_at_k`

### 4.2 HITL Load

- 人工升级总次数（全任务或仅成功任务，报告中定义清楚并前后一致）
- 对应：`escalations_count` → `total_hitl_load` / `avg_hitl_load`
- 越低越好：理想是高 TCR + 低 HITL

### 4.3 Token 成本三分解

| 部分 | 来源建议 |
| :--- | :--- |
| Policy tokens | `PolicyDecision.token_cost` |
| Reviewer tokens | `ReviewerDecision.token_cost` |
| Agent tokens | AgentDojo / LLM agent 调用统计（需与汤墨言对齐接入点） |

`BenchmarkSummary` 中已有：`total_policy_tokens` / `total_reviewer_tokens` / `total_agent_tokens`

## 5. 评测流水线开发指导

> 提醒：此处的 `tasks` 最终应来自 **AgentDojo 任务集**，不是自建 sandbox 任务（见第 3 节）。

### 5.1 填充 `EvaluationRunner.run_benchmark_for_budget()`

文件：`evaluation/runner.py`

建议循环骨架：

```text
for each task in tasks:
    budget = BudgetTracker(initial_budget=budget_k)
    gate.clear_audit_log()   # 如需要
    运行 Agent（每个 tool call 都走 gate.intercept）
    统计:
      - 是否任务成功
      - 是否执行了未授权调用
      - escalations_count
      - policy_tokens / reviewer_tokens / agent_tokens
      - failure_category（如可判定）
    写入 TaskEvaluationResult
汇总得到 BenchmarkSummary
```

### 5.2 产出 TCR 曲线

```python
runner.evaluate_tcr_curve(tasks)  # 默认 k in [0,1,2,5,10]
```

需要对每个策略（Full-approve / Full-escalate / Rule-based / Smart）各跑一遍，保存结果并绘制 `TCR vs k`。

## 6. 归因分析与报告指导

### 6.1 Failure Case 两类归因

#### Over-conservative（过度保守）

- 本可安全执行的调用被误拦 → 任务完成率下降
- 常见原因：规则过严、Smart Policy 过敏、`k` 太小导致 escalate 退化拒绝

#### Over-permissive（过度放任）

- 未授权 / 攻击诱导调用被放行 → 安全性失败
- 常见原因：无防护基线、策略未识别注入、Reviewer Prompt 过松

对应结构：`evaluation/metrics.py` → `FailureCategory`

```python
FailureCategory(
    task_id="...",
    category="over_conservative" | "over_permissive",
    failed_tool_call="tool_name / call_id",
    reason="一句话归因",
    trajectory_snippet=[...],
)
```

每个失败类型建议至少准备 **3 个**代表性案例，可放在 `evaluation/case_studies/`。

### 6.2 Escalation-value（升级价值）分析

目标：证明智能策略把有限人工预算花在了更关键的调用上。

可分析：

1. 升级命中率（escalate 后 Reviewer Deny 的比例）
2. 反事实：若这次不升级会怎样
3. 边际收益：每增加 1 个 `k`，TCR 提升多少
4. 与 Full-escalate 对比：是否更少 HITL、接近的 TCR

建议在 `evaluation/analysis.py` 实现，读取 `results/*.json`。

### 6.3 README 与 Report

**README（简洁）：** 背景、快速运行、目录、主结果图、分工

**Report（完整）建议章节：**

1. Background & Problem  
2. Method（Gate / Policy / Reviewer / Budget）  
3. Baselines vs Smart Policy  
4. Evaluation Setup  
5. Results（TCR@k、HITL、Token Cost）  
6. Failure Analysis  
7. Escalation-value Analysis  
8. Limitations & Future Work  
9. Division of Labor
